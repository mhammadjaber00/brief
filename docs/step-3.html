Step Three.

SPL comprehension — turn obfuscated, macro-laden searches into structured explanations.

§ Context

Where we are.

The scanner from Step 02 enumerates every object in an app and flags which ones lack descriptions. For each undescribed saved search, Stage 3 (generation) needs to know what the SPL actually does — not just what it textually looks like.

SPL is hard to reason about textually: macros nest opaquely (a search referencing `cs_network_traffic` reveals nothing without macro expansion), pipes can be deeply chained, and field references depend on extracted vs. raw context. Step 03 offloads this comprehension to Splunk's own saia_explain_spl tool via the MCP Server. A local Ollama fallback handles offline scenarios.

§ Goal

What Step 03 delivers.

  • A macro expander that inlines every backtick-referenced macro before any SPL is sent to the explainer
  • An saia_explain_spl wrapper that calls the MCP Server in live mode
  • A local Ollama-based fallback for offline mode (no MCP available)
  • A unified SPLExplanation Pydantic model with the structured output of both paths
  • A simple caching layer so the same SPL is never re-explained within a run
Read `skill.md` first. Then build Brief's SPL comprehension layer — Stage 2 of the pipeline. Files to create src/brief/spl/macro_expander.py A `MacroExpander` class that takes: - The full `macros.conf` parsed dict (from Step 02's `ConfParser`) - A raw SPL string And returns the SPL with every backtick-referenced macro inlined. Rules: - Macros use backtick syntax: `macro_name` or `macro_name(arg1, arg2)` - Argument substitution: in a macro with `args = field1, field2`, references to `$field1$` in the body get replaced - Handle nested macros — expand recursively until no more backticks remain - Cap recursion depth at 10 to prevent runaway expansion on malformed configs Public method: `expand(spl: str, macros: dict) -> str`. Returns the fully-inlined search. src/brief/spl/models.py ```python class SPLExplanation(BaseModel): indexes_queried: list[str] sourcetypes_filtered: list[str] fields_extracted: list[str] transformations: list[str] # human-readable: "groups by user", "counts events", etc. output_shape: str # one-line description of result table summary: str # 2-3 sentences source: Literal["saia", "ollama"] # which backend produced this ``` src/brief/spl/explainer_saia.py The `saia_explain_spl` MCP wrapper. Public function: `explain_via_saia(spl: str, mcp_client) -> SPLExplanation`. - Uses `splunklib.ai` to call the MCP tool - Authentication via bearer token from environment / config - Parse the natural-language response into the structured `SPLExplanation` shape using a second LLM pass (the explainer returns prose; we need structured) - Or use the model's structured-output mode if the MCP tool supports it - On failure: raise a typed exception, don't silently fall through. The caller decides whether to fall back to Ollama. src/brief/spl/explainer_ollama.py Local fallback using Ollama with `llama3.1:8b-instruct`. Public function: `explain_via_ollama(spl: str) -> SPLExplanation`. - Uses the `ollama` Python package - Sends a structured prompt asking the model to identify indexes, sourcetypes, fields, transformations, and output shape - Uses Pydantic schema-guided output (Ollama supports JSON mode) - Returns the same `SPLExplanation` shape so downstream code is backend-agnostic The system prompt for Ollama lives in `src/brief/spl/prompts.py`. It should explicitly teach the model that SPL is pipe-delimited, that indexes come before the first pipe, that `| stats`, `| chart`, `| timechart` are aggregation commands, etc. Keep the prompt focused — under 400 tokens. src/brief/spl/__init__.py Unified entry point: `explain(spl: str, macros: dict, mode: Literal["live", "offline"]) -> SPLExplanation`. - First call `macro_expander.expand()` to inline macros - If `mode == "live"`, call `explain_via_saia()`; on failure, log and fall back to Ollama - If `mode == "offline"`, call `explain_via_ollama()` directly - Wrap with a simple in-memory cache keyed on the expanded SPL — same SPL is never re-explained within a session Constraints - DO NOT call generation models yet — that's Step 04 - DO NOT emit any descriptions — Stage 3's job - The explainer's output must be backend-agnostic — downstream code must not care whether saia or Ollama produced the explanation - Cache key must be the expanded SPL, not the raw — different macro environments may yield different expansions of the same raw search Testing - Unit-test macro expansion against fixtures: simple, nested, with-args, recursion-cap - Mock the saia path with a fixture response — don't make real MCP calls in unit tests - Integration test: real Ollama call on 3 sample searches from the Step 02 fixture TA. Assert the explanation includes the correct indexes. - Cache test: call `explain()` twice on the same SPL; assert the second call doesn't hit the backend Acceptance - `pytest tests/test_spl.py` passes - Manual test: pick a saved search from your fixture TA that uses a macro. Run `explain()` on it in offline mode. § Acceptance

How you know Step 03 is done.

  • Macro expansion handles nested macros without infinite loops
  • Both explain_via_saia and explain_via_ollama produce SPLExplanation objects with the same shape
  • Live mode falls back to Ollama gracefully when MCP is unreachable
  • The cache is keyed correctly — repeated calls on the same expanded SPL skip the backend
  • An end-to-end test on the Step 02 fixture TA produces explanations for at least 80% of its saved searches without errors
