§ 01 — The problem

Splunk asked for this tool. Nobody built it.

On February 4, 2026, Splunk released its Model Context Protocol Server to general availability, and in doing so fundamentally changed what a Splunk app is for. From that day forward, an app's users were no longer only humans staring at dashboards — they were AI agents, programmatically asking the Splunk platform questions on behalf of those humans.

Two months later, in April 2026, Splunk published Making Your Apps "Agent-Ready" — an explicit directive to the third-party developer community to optimize their app metadata for AI-agent consumption. The passage at the heart of it reads:

"AI agents rely on semantic context to understand which tool to call. If your knowledge objects aren't descriptive, the agent is essentially flying blind." Splunk Product News · April 2026

Splunk's prescription was to add description = ... lines to every savedsearches.conf, macros.conf, and dashboard XML file in every app on Splunkbase. The recommended tool: the Splunk Developer Advisory & Support team, available for free one-on-one consulting.

There are over 2,800 apps on Splunkbase. The DAS team is a handful of humans. No tool exists to do this work at scale — verified against Splunk's announced 2026 roadmap, against SURGe's open-source portfolio, against every third-party agent vendor (Dropzone, CrowdStrike, SentinelOne, Google, Microsoft), and against the closest existing developer tool, splunk-app-action, which handles CI/CD packaging and AppInspect compliance but says nothing about agent-readiness.

Brief is the tool Splunk asked for but didn't build.

✦
§ 02 — What Brief is

An agent that prepares apps for agents.

Brief reads a Splunk app's metadata, understands what its saved searches actually do, and generates the semantic descriptions that AI agents need in order to discover and call those searches as tools through the Splunk MCP Server.

It runs in three shapes: as a Splunk app installed alongside the apps it audits, as a command-line tool pointed at a folder on disk, or as a GitHub Action that runs on every pull request to a Splunk app repository.

It is built on the splunklib.ai agent framework (newly released in splunk-sdk-python v3.0.0 on May 12, 2026 — six days before the hackathon kickoff), uses Foundation-Sec-1.1-8B-Instruct and gpt-oss-20b as Splunk Hosted Models, and calls saia_explain_spl from the Splunk AI Assistant for SPL to understand SPL it's never seen before.

The output is three artifacts:

  • An agent-readiness score from 0 to 100, computed per object and rolled up per file and per app.
  • A unified-diff PR proposing every description change for human review — Brief never overwrites, it proposes.
  • An MCP manifest YAML enumerating which of the app's saved searches should be exposed as agent-callable tools, with descriptions, MITRE tags where relevant, and recommended RBAC scopes.

§ 03 — The pipeline

Four stages, one agent loop.

Brief is implemented as a single splunklib.ai Agent with a ToolRegistry containing the parsers, MCP callers, and Hosted Model wrappers it needs. The agent reasons across all four stages within one execution; the stages below describe the logical decomposition, not separate processes.

Fig. 1 — The Brief pipeline

Stage 01

Scan

Brief parses the app's metadata files (the full priority list lives in §04) and computes four signals per scannable object: presence (does a description exist), quality (is it more than a tautological restatement of the name — scored by an LLM rubric), coverage (what percentage of objects in this file are adequately described), and safety (would the search pass MCP guardrails when called: ≤60 seconds, ≤1000 events, no destructive SPL commands).

The scan runs in either offline mode (a folder on disk: your repo, a Splunkbase package) or live mode (a Splunk instance accessed through the MCP Server's splunk_get_knowledge_objects tool). Live mode is useful for auditing what's actually deployed in production versus what's checked into the repo — they drift.

Stage 02

Read SPL

For each saved search that lacks an adequate description, Brief invokes saia_explain_spl from the Splunk AI Assistant for SPL. This returns a structured explanation of the search: which indexes are queried, which sourcetypes are filtered, which fields are extracted, which transformations applied, and what the output table looks like.

Macro references (backtick-delimited identifiers like `internal_assets`) are expanded inline before the explanation is requested, so the explanation reflects the full search the agent would actually run, not a fragment.

Stage 03

Generate

With the SPL explanation as grounding context, Brief invokes a Splunk Hosted Model — Foundation-Sec-1.1-8B-Instruct for security-classified apps, gpt-oss-20b for general/observability apps — and requests a structured description matching a Pydantic schema. splunklib.ai's structured output support enforces the schema; malformed outputs are auto-retried.

class GeneratedDescription(BaseModel):
    description: str           # 80–240 chars
    primary_use_case: str
    output_fields: list[str]
    mitre_techniques: list[str] | None   # security apps only
    estimated_runtime: Literal["fast", "medium", "slow"]
    suitable_for_agent: bool

Foundation-Sec is chosen for security apps because it was trained on 5 billion tokens of security data including MITRE ATT&CK technique reasoning and threat actor profiles. It produces dramatically better descriptions for security saved searches than a general-purpose model — and crucially, it surfaces accurate MITRE technique tags as a side effect, which makes the resulting MCP manifest more useful to downstream calling agents.

Stage 04

Emit

Three artifacts land in the output directory:

  • A readiness report (HTML + JSON) showing the score breakdown per object, per file, and per app.
  • A unified-diff PR file against the app's .conf files. Standard git apply-compatible diff. Every change is human-reviewable before merge — Brief proposes, you approve.
  • An MCP manifest YAML (mcp_manifest.yaml) consumed by the Splunk MCP Server, enumerating the app's agent-callable saved searches with descriptions, output fields, MITRE tags, and recommended RBAC roles.

§ 04 — What Brief scans

The agent-callable surface, mapped.

Not every file in a Splunk app affects what an AI agent can do. Brief reads in priority order:

File Why it matters Priority
savedsearches.conf Every stanza is a candidate tool exposed through splunk_run_saved_search. Description quality determines whether agents call it. Primary
macros.conf Reusable SPL fragments composed into saved searches. Brief expands every macro reference inline. Primary
app.manifest · app.conf The app's identity. Agents use the top-level description to decide whether to explore at all. Primary
metadata/default.meta RBAC. Brief flags any object the standard mcp_user role can't reach. Primary
data/ui/views/*.xml Dashboard panels embed searches that never made it to savedsearches.conf. Brief proposes promoting them. Secondary
eventtypes.conf · tags.conf Semantic event classification. Agents reason in these vocabularies for cross-app discovery. Secondary
transforms.conf · lookups/ Field extractions and lookup tables. Field names need to read like English for agents to construct meaningful queries. Secondary
commands.conf Custom SPL commands the app adds to the engine. Agents need descriptions to know when to use them. Secondary
bin/ · .py · README · CSV payloads Implementation, not metadata. Brief never modifies code. Skipped
Why not just regex for missing descriptions?
A regex can find empty description fields. It can't tell you that description = "auth search" is a tautology that gives the agent no actionable information. The quality signal — the difference between a present description and a useful one — is what makes Brief LLM-shaped rather than parser-shaped.

§ 05 — What Brief outputs

Three artifacts. One source of truth.

The agent-readiness score

A composite 0–100 number with this weighting:

  • Presence (40%) — does a description exist?
  • Quality (30%) — is it more than a tautology, scored 0–10 against an LLM rubric?
  • Coverage (20%) — what fraction of scannable objects in this file are described?
  • Safety (10%) — would the search pass MCP guardrails (runtime, event limit, no destructive SPL)?

The score is directionally meaningful, not exact. A 14% → 92% improvement is the kind of headline number that makes the demo land.

The diff PR

A standard unified diff (git apply-compatible) against the app's .conf files. Brief never overwrites; it proposes. Every change is human-reviewable in a git PR before merge. This matters for trust — Foundation-Sec might write a description that is technically accurate but misses the original author's intended use case.

The MCP manifest

A YAML file (mcp_manifest.yaml) listing every agent-callable saved search, its description, expected inputs, output fields, MITRE tags where applicable, and recommended RBAC scope. This manifest is consumed at app-install time by the Splunk MCP Server — it is the contract between an app and the agent ecosystem.

app: TA_security_monitoring
tools:
  - name: get_failed_auth_24h
    saved_search: get_failed_auth_24h
    description: |
      Returns count of failed Linux SSH logins (event 4625) by user and
      source IP in the last 24 hours. Use for credential stuffing or
      brute force investigations.
    output_fields: [user, src_ip, count]
    mitre_techniques: [T1110.001, T1078]
    rbac_role: mcp_user
    estimated_runtime: fast

§ 06 — The Splunk AI stack

Four capabilities, one agent.

Brief leverages every primary surface in Splunk's announced 2026 AI roadmap. This is deliberate: the more of Splunk's surface area the build touches, the stronger the Technological Implementation score (the hackathon's first tiebreaker criterion).

splunklib.ai (v3.0.0)
The agent loop. Brief instantiates a single Agent with a ToolRegistry containing parsing utilities, MCP tool callers, and Hosted Model wrappers. The agent runs to completion within default AgentLimits (max_tokens=200000, max_steps=100, timeout=600s). Released May 12, 2026 — six days before hackathon kickoff. Requires Python 3.13. Two breaking-change pitfalls to internalize: agent state is tracked via Agent.messages, not the older .response attribute (renamed in PR #743); and token/step/timeout middlewares live in splunklib.ai.limits, not splunklib.ai.hooks (moved in PR #759). Repository →
Splunk MCP Server (v1.1.2)
Both the data source (Brief calls splunk_get_knowledge_objects and splunk_get_metadata in live mode) and the deployment target (Brief emits an MCP manifest the server consumes). GA February 4, 2026. Authenticates via encrypted bearer tokens generated from inside the MCP Server app — the legacy Settings → Tokens path has been deprecated since v1.0.0. OAuth 2.1 in v1.1.0 is a closed preview restricted to Splunk Cloud Platform customers, requires Twix 10.3.2512.X, and needs ~1 week of Splunk Identity Service coordination to enable — do not rely on it for the hackathon. Static bearer tokens are the supported path. Splunkbase listing →
Splunk Hosted Models
Foundation-Sec-1.1-8B-Instruct for security apps, gpt-oss-20b for general apps. GA February 18, 2026. Available exclusively on Splunk Cloud Platform. Brief's CLI and GitHub Action modes therefore ship with a local inference adapter (Ollama hosting Llama-3.1-8B-Instruct) as a mandatory offline fallback — Foundation-Sec itself is a continuously pre-trained Llama-3.1-8B variant, so a local Llama base preserves architectural symmetry even when the cloud model isn't reachable. Capability page →
Splunk AI Assistant for SPL
Brief calls saia_explain_spl once per undescribed saved search, grounding the generation step in what the SPL actually does rather than what it textually looks like. This offloads the error-prone task of SPL parsing to a purpose-built Splunk component — macros are expanded inline before invocation so the explanation reflects the full search the agent would actually run. § 08 — Operating modes

Three shapes, one core.

As a Splunk app

Brief installs on Splunk Cloud alongside the apps it audits. It uses Splunk's own scheduler to run on a cron and exposes a dashboard showing the readiness score for every other installed app. This is the internal compliance tool shape — a SOC team can install Brief, see which of their installed apps are agent-ready, and prioritize remediation.

As a CLI

A single Python entrypoint: brief scan path/to/app --output report/. Runs entirely offline against a folder on disk. No Splunk instance required. This is the developer workflow shape — a Splunk app author runs it during development before pushing to Splunkbase.

As a GitHub Action

Plugs into existing app-development workflows: uses: brief/brief-action@v1 opens a PR with proposed description changes on every pull request. This is the CI/CD shape — agent-readiness becomes part of the merge gate.

All three shapes share the same core agent. The differences are inputs (filesystem vs. live MCP), outputs (filesystem vs. GitHub API vs. Splunk dashboard), and scheduling (one-shot vs. cron vs. webhook).

§ 09 — Why this wins

Track fit, bonus stacking, criteria mapping.

Platform & Developer Experience track

The track description has three sub-clauses. Brief satisfies all three cleanly:

  • "Enhance the developer experience" — Brief is for Splunk app developers. It takes the manual metadata-writing work that Splunk's DAS team currently does as free 1-on-1 consulting and automates it.
  • "Automate workflows" — the entire product is automation: scan app → score readiness → generate descriptions → produce diff PR → emit MCP manifest. Zero manual editing.
  • "Simplify how applications interact with Splunk data and API" — Brief fixes the metadata layer that determines whether the Splunk MCP Server (the agent-facing API surface) can discover and call an app's saved searches at all.

Three stackable bonus prizes

The hackathon's bonus prizes are explicitly stackable with both the grand prize and the track prize. Brief plausibly captures three of them simultaneously:

  • Best Use of Splunk Developer Tools ($1,000) — Brief depends on the bleeding-edge splunklib.ai agent framework (PRs #743, #759, #724 are all relevant), uses AppInspect for safety validation, and ships in both Splunkbase-package and GitHub Action shapes. Most surface area of any plausible submission.
  • Best Use of Splunk MCP Server ($1,000) — Brief is both an MCP client (calls splunk_get_knowledge_objects, splunk_get_metadata, saia_explain_spl) and a producer of MCP manifests that the server consumes at install time. Few projects will inhabit both sides of the protocol.
  • Best Use of Splunk Hosted Models ($1,000) — Foundation-Sec-1.1-8B-Instruct is used non-trivially for MITRE technique extraction (security apps), with gpt-oss-20b for general apps. The local fallback adapter pattern also demonstrates production-aware thinking about Cloud-only constraints.

Combined potential: grand prize ($7,000) + track prize ($3,000) + three bonuses ($3,000) = $13,000 if Brief wins everything plausible. Realistic floor with track prize + one bonus is $4,000.

§ 11 — Resolved constraints

What due diligence settled.

A second pass of research (documented in the project archive) resolved the open questions from the spec phase. The answers below dictate concrete architectural decisions Brief carries from week one.

Foundation-Sec callability outside Splunk Cloud
Confirmed Cloud-only. Splunk Hosted Models are documented as available exclusively on Splunk Cloud Platform; calls happen internally via the ai SPL command or the ML-SPL API within the cloud tenant. Brief's CLI and GitHub Action modes therefore must ship a local inference adapter. Ollama hosting Llama-3.1-8B-Instruct is the chosen fallback; Foundation-Sec is itself a Llama-3.1-8B continual-pretrain, so the offline base preserves architectural shape.
splunk_run_saved_search beta stability
Beta; structurally resilient anyway. The tool was introduced in April 2026 and is provided "as is" without service-level guarantees. Because Brief emits an abstracted mcp_manifest.yaml rather than hard-coding tool invocations, a schema shift during the hackathon window requires only updating the YAML emission template in Stage 4 — the core agent loop is unaffected.
AppInspect rules for description quality
No native rule exists. AppInspect validates structural correctness (packaging, syntax, dependency versions — e.g., it will throw a fatal on outdated SDK bindings like v1.6.6 instead of v1.7.3+). It has no LLM-based semantic quality check. Brief's LLM-rubric scoring is therefore novel, not redundant. Future upstream contribution to AppInspect is a roadmap item worth surfacing in the README — judges will read it as forward-looking ecosystem thinking.
RBAC propagation in live mode
Depends on per-app metadata. splunk_get_knowledge_objects respects standard Splunk RBAC; a service account with mcp_user + mcp_tool_execute can only enumerate objects whose default.meta permissions admit that role. For Brief's Splunk app deployment shape, the service account should run with sc_admin + mcp_tool_admin to ensure comprehensive cross-app audit. CLI and Action modes operate on local filesystems so this constraint doesn't apply.
Demo target app
Any older Technology Add-on (TA-*) on Splunkbase with sparse description coverage qualifies. The demo prep step in the build plan picks one based on a quick agent-readiness reconnaissance score across candidate TAs.
Downstream complement
The Splunk Threat Research Team (STRT) recently published a TA that parses JSON-RPC output from MCP Servers for security monitoring. Brief's standardized manifests feed cleanly into that observability layer — generated metadata flows into the JSON-RPC logs the STRT TA analyzes. Mention this in the README and the demo video as ecosystem fit.
