Step Eight.

Brief as a GitHub Action — agent-readiness becomes part of the pull-request merge gate.

§ Context

Where we are.

The CLI runs locally. The Splunk app runs inside Splunk Cloud. The third deployment shape closes the loop: a GitHub Action that runs on every pull request to a Splunk app repository, auto-opening a follow-up PR with proposed description changes if the readiness score drops below a configurable threshold.

This is the CI/CD shape. It makes agent-readiness a code-review concern, not an afterthought. Combined with the diff-PR design, it lets human reviewers see exactly what Brief proposes — a perfect alignment with the judges' explicit "human-in-the-loop" prioritization.

§ Goal

What Step 08 delivers.

  • An action.yml defining inputs, outputs, and execution
  • A Dockerfile containerizing Brief with Python 3.13 + Ollama for offline inference
  • PR auto-opening logic using the GitHub REST API
  • A PR comment summarizing the readiness score and key changes
  • A working test repo demonstrating the Action in use
  • Marketplace-ready packaging (icon, README, branding)
Read `skill.md` first. Build Brief as a GitHub Action — the CI/CD deployment shape. Files to create action.yml (repo root) ```yaml name: 'Brief — Splunk Agent-Readiness Audit' description: 'Audit a Splunk app for AI-agent-readiness on every PR.' author: '' branding: icon: 'check-circle' color: 'orange' inputs: target-path: description: 'Path to the Splunk app to audit (relative to repo root)' required: true default: '.' model-backend: description: 'Which model backend to use: hosted (Splunk Cloud) or local (Ollama)' required: false default: 'local' output-dir: description: 'Where to write artifacts' required: false default: 'brief-output' open-pr: description: 'Auto-open a follow-up PR with proposed description changes' required: false default: 'true' fail-below-score: description: 'Fail the action if readiness score is below this threshold' required: false default: '70' splunk-mcp-url: description: 'Optional Splunk MCP Server URL (hosted backend only)' required: false splunk-mcp-token: description: 'Optional Splunk MCP Server bearer token (hosted backend only)' required: false outputs: score: description: 'Overall agent-readiness score (0-100)' pr-number: description: 'Number of the auto-opened follow-up PR, if any' runs: using: 'docker' image: 'Dockerfile' ``` Dockerfile (repo root) ```dockerfile FROM python:3.13-slim # Install Ollama for local inference fallback RUN apt-get update && apt-get install -y curl ca-certificates && \ curl -fsSL https://ollama.com/install.sh | sh && \ rm -rf /var/lib/apt/lists/* # Install Brief COPY . /brief/ WORKDIR /brief/ RUN pip install --no-cache-dir -e . # Pre-pull the model so first-run isn't slow # Note: this adds ~5GB to image size. Consider lazy pull on first invocation. RUN ollama serve & sleep 2 && ollama pull llama3.1:8b-instruct && pkill ollama ENTRYPOINT ["/brief/scripts/action-entrypoint.sh"] ``` scripts/action-entrypoint.sh ```bash #!/bin/bash set -e # Start Ollama in background if using local backend if [ "$INPUT_MODEL_BACKEND" = "local" ]; then ollama serve & sleep 3 fi # Run audit brief audit "$INPUT_TARGET_PATH" \ --output "$INPUT_OUTPUT_DIR" \ --mode "${INPUT_MODEL_BACKEND}" \ --output-format json # Extract score SCORE=$(jq -r '.overall_score' "$INPUT_OUTPUT_DIR/score.json") echo "score=$SCORE" >> $GITHUB_OUTPUT # Open follow-up PR if requested if [ "$INPUT_OPEN_PR" = "true" ] && [ -s "$INPUT_OUTPUT_DIR/descriptions.diff" ]; then python /brief/scripts/open_pr.py fi # Fail if below threshold if (( SCORE < INPUT_FAIL_BELOW_SCORE )); then echo "::error::Readiness score $SCORE is below threshold $INPUT_FAIL_BELOW_SCORE" exit 1 fi ``` scripts/open_pr.py Python script that: 1. Reads $INPUT_OUTPUT_DIR/descriptions.diff 2. Creates a new branch brief/auto-update-$(date +%s) 3. Applies the diff to the branch 4. Pushes the branch 5. Opens a PR via the GitHub REST API with: - Title: Brief: agent-readiness improvements ($SCORE → projected $PROJECTED) - Body: a markdown summary of changes, the readiness report excerpt, and a link to the HTML report (uploaded as an artifact) 6. Adds a comment to the original PR with: Brief score: $SCORE/100. See follow-up PR #$NEW_PR. Uses GITHUB_TOKEN from the action environment. Use the official PyGithub library or raw requests against the REST API. .github/workflows/test-action.yml Self-test: in this same repo, run the Action against the tests/fixtures/sample-ta-1/ fixture on every PR. Catches regressions in the action wiring itself. examples/sample-repo/ Optional but recommended: a separate small sample repo with a Splunk app and a workflow file using the Action. Link to this repo from the README. Judges and Splunkbase reviewers will check it. README.md updates Document the Action's usage prominently: ```yaml # Example .github/workflows/audit.yml in a Splunk app repo on: pull_request: paths: ['**.conf', '**/views/*.xml'] jobs: audit: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - uses: /brief@v1 with: target-path: '.' fail-below-score: 70 ``` Constraints - The Action container image must stay under reasonable size for CI (target: under 8 GB including Ollama + Llama-3.1-8B) - Never log the GITHUB_TOKEN or any Splunk credentials - The Action must handle the case where there are no changes (empty diff) gracefully — exit 0 with a message - Use the GITHUB_TOKEN's automatic permissions; never require a custom PAT in the simple case Testing - Create a public test repo with a Splunk app, add the workflow file, open a PR - Verify the Action runs, posts a comment, opens a follow-up PR - Verify the score threshold causes the action to fail when it should - Verify the action passes cleanly when score is above threshold Acceptance - The Action runs end-to-end on a real test repo - A follow-up PR is auto-opened with valid description changes - The action.yml is documented well enough that someone reading just the README can use it - The Docker image builds successfully on GitHub-hosted runners
