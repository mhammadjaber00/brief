Step Four.

Description generation — turn structured SPL explanations into agent-callable metadata.

§ Context

Where we are.

Step 02 enumerates objects. Step 03 explains their SPL. Step 04 turns those explanations into the actual descriptions Splunk's MCP Server will serve to calling agents. This is also where the splunklib.ai Agent is finally assembled — the parsing tools, SPL explainer, and generators are registered as a unified ToolRegistry.

Two backend paths: Splunk Hosted Models (Foundation-Sec-1.1-8B-Instruct for security apps, gpt-oss-20b for general apps) when running on Splunk Cloud, and Ollama with Llama-3.1-8B-Instruct when running offline.

§ Goal

What Step 04 delivers.

  • The Pydantic GeneratedDescription schema enforced via splunklib.ai structured output
  • A Hosted Models adapter calling Foundation-Sec / gpt-oss-20b via Splunk Cloud's inference endpoint
  • An Ollama adapter producing schema-compliant output offline
  • App classification heuristic (security vs general) so the right model is picked
  • The full splunklib.ai Agent assembled with its ToolRegistry and run end-to-end on a fixture TA
  • A description-quality LLM rubric for the quality signal (deferred until now because it needs a generation backend)
Read `skill.md` first. Critical reminders before starting: agent state is `Agent.messages` (PR #743). Limits live in `splunklib.ai.limits`, not `.hooks` (PR #759). `id` is required on tool calls (PR #724). Hosted Models are Splunk Cloud only — your CLI / Action paths use Ollama. Build Brief's generation layer — Stage 3 of the pipeline. Files to create src/brief/generator/schema.py The Pydantic schema enforced on every generated description: ```python class GeneratedDescription(BaseModel): description: str = Field(min_length=80, max_length=240) primary_use_case: str = Field(max_length=120) output_fields: list[str] mitre_techniques: list[str] | None = None estimated_runtime: Literal["fast", "medium", "slow"] suitable_for_agent: bool reasoning: str = Field(max_length=300) ``` Plus a `QualityRubric(BaseModel)` for evaluating existing descriptions: ```python class QualityRubric(BaseModel): quality_score: int = Field(ge=0, le=10) is_tautology: bool # "auth search" describing get_auth — yes specifies_data_source: bool # mentions index/sourcetype/event_id specifies_use_case: bool # mentions when to call it actionable: bool # an agent could decide based on this reasoning: str ``` src/brief/generator/prompts.py Two prompt templates: 1. `GENERATE_DESCRIPTION_PROMPT` — instructs the model to produce a `GeneratedDescription` from an `SPLExplanation`. Critical instructions: lead with verb, name event IDs / indexes if mentioned in explanation, state canonical use case, put MITRE techniques in the field not the prose, avoid hedging. 2. `EVALUATE_QUALITY_PROMPT` — instructs the model to score an existing description against the `QualityRubric`. Keep prompts under 500 tokens each. Test them iteratively. src/brief/generator/hosted.py Splunk Hosted Models adapter. Uses `splunklib.ai` to call: - `Foundation-Sec-1.1-8B-Instruct` for security-classified apps - `gpt-oss-20b` for general apps Public functions: - `generate_description_hosted(explanation: SPLExplanation, model_id: str) -> GeneratedDescription` - `evaluate_quality_hosted(description: str, explanation: SPLExplanation, model_id: str) -> QualityRubric` Both use Pydantic schema-guided output via `splunklib.ai`'s structured output support. On schema validation failure, the SDK auto-retries — let it. src/brief/generator/local.py Ollama adapter using the same signatures. Uses `llama3.1:8b-instruct` and Ollama's JSON mode with Pydantic schema validation. Returns the same `GeneratedDescription` and `QualityRubric` types so downstream code is backend-agnostic. src/brief/generator/classifier.py Lightweight rule-based app classifier. Public function: `classify_app(report: AppScanReport) -> Literal["security", "general"]`. Heuristic: - Check `app.conf` description for keywords: "security", "threat", "SOC", "SIEM", "compliance" - Scan saved searches for security indexes: `wineventlog`, `linux_secure`, `netflow`, `firewall`, `proxy`, `dns_query` - Scan eventtypes/tags for MITRE-style names: `attack`, `breach`, `intrusion` - Default to "general" if no signals Returns the classification so the orchestrator picks the right model. src/brief/generator/__init__.py Unified entry point: - `generate(explanation: SPLExplanation, mode: Literal["live", "offline"], app_class: str) -> GeneratedDescription` - `evaluate(description: str, explanation: SPLExplanation, mode: str, app_class: str) -> QualityRubric` src/brief/agent.py The full splunklib.ai Agent assembled here. This is the orchestrator that runs Stages 1→4 in one execution. ```python from splunklib.ai import Agent, ToolRegistry, AgentLimits def build_brief_agent(mode: str, app_class: str) -> Agent: registry = ToolRegistry() registry.register("scan_app", scanner.scan_app) registry.register("expand_macros", macro_expander.expand) registry.register("explain_spl", spl.explain) registry.register("generate_description", generator.generate) registry.register("evaluate_quality", generator.evaluate) limits = AgentLimits( max_tokens=200_000, max_steps=100, timeout=600, ) return Agent( tools=registry, limits=limits, # state tracked via .messages, not .response (PR #743) ) ``` Public entry: `audit_app(path: Path, mode: str) -> tuple[AppScanReport, dict[object_name, GeneratedDescription]]`. This is the one-call orchestrator the CLI will use. Constraints - DO NOT emit any output artifacts yet — diff, manifest, report all come in Step 05 - DO NOT implement live MCP writes back to Splunk — Brief never writes to a running Splunk in live mode, only reads - Schema validation failures retry automatically via splunklib.ai — don't catch them as errors - For Hosted Models: tokens come from environment, never logged - For Ollama: assume `localhost:11434` with `llama3.1:8b-instruct` already pulled (Step 01 set this up) Testing - Unit test schema enforcement: feed garbage to the schema, assert ValidationError - Mock Ollama responses with fixture JSON; test the parsing path - Integration test: run `audit_app()` end-to-end on the Step 02 fixture TA in offline mode. Assert that for each undescribed saved search, a `GeneratedDescription` with ≥80 chars is produced. - Quality rubric test: feed it a known-tautological description ("auth search"); assert `is_tautology=True` and `quality_score < 4`. Acceptance - The Agent runs to completion within 5 minutes on a 30-saved-search TA in offline mode - Generated descriptions consistently lead with a verb (manually inspect 10) - MITRE techniques are populated for security-classified apps (manually verify 3) - The Hosted Models path works against your Splunk Cloud trial — defer if Cloud provisioning is still pending
§ Acceptance

How you know Step 04 is done.

  • audit_app() runs end-to-end in offline mode on the fixture TA, producing valid GeneratedDescription objects
  • App classifier correctly tags your fixture TA
  • Quality rubric distinguishes good from tautological descriptions (eyeball test on 5 examples)
  • Hosted Models path is implemented and tested against Splunk Cloud (or stubbed with a clear TODO if Cloud isn't yet provisioned)
  • Agent state is correctly tracked via .messages — verify by inspecting the agent run trace
